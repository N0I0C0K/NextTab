# 推荐性能评估

评估日期：2026-10-03（Asia/Shanghai）。结论：评分计算的规模受日志上限约束；打开标签乘 1.3 没有改变评分复杂度。长列表按页挂载并共享标签 URL 分组，避免逐行重复解析。接近日志上限时，降速评分仍可能超过 50 ms；快照读取和“最近常用”的历史 API 查询仍是等待来源。

## 复杂度

记 `E` 为日志事件数，`P` 为页面数，`H` 为历史 URL 数，`V` 为历史 API 返回的访问记录总数，`T` 为已打开标签数。

| 操作               | 时间复杂度                                         | 额外空间与边界                                                                                                   |
| ------------------ | -------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| 最近回访评分       | `O(E log E + P log P)` 上界                        | `O(E + P)`；按 view 配对、按页面分组，重叠去重后按日期分配时长并计算中位数；每段最多涉及 8 个当地日期            |
| 最近访问候选组装   | 评分成本外加 `O(H log H + T + P log P)`            | `H ≤ 1000`；历史去重后合并当前标签，按最终得分排序，无前台日志的基础分为 0                                       |
| 读取日志快照       | `O(E + P)`，外加到期清理                           | 全部原始记录读取一次；序列化内容最多 2 MiB，保留 10 天，评分使用滚动 7 天                                        |
| 普通进入／离开     | 固定数量的 IndexedDB 请求，索引查找按存储规模增长  | 不使用定时器，不随停留时长写入日志；时间和得分在读取时计算                                                       |
| 部分过期／容量淘汰 | 与删除的 view 数及索引操作有关                     | 删除成对记录；页面是否仍被引用用 `pageId.getKey()` 判断，不扫描该页面的全部引用                                  |
| 全部记录过期       | 原生 IndexedDB `clear()`，存储引擎成本随数据量增长 | 不再为每个 view 发起独立读取、删除和页面更新请求                                                                 |
| 最近常用           | `O(H + V + P log P)`，另有最多 `H` 次 API 调用     | `H ≤ 1000`，最多 6 个并发；每个 URL 仅保留范围内每一天的一条记录，最多 30 条                                     |
| 长列表渲染         | URL 分组／匹配 `O(T + min(P, 20))`                 | 每个列表共用一次 Map 分组，额外 `O(T)`；每页最多挂载 20 行；站点多标签行的窗口序号文案最坏仍 `O(min(P, 20) × T)` |
| 搜索               | `O(P)`（另计标题和 URL 字符串长度）                | 对全部候选搜索，搜索变化重置分页；不会遗漏尚未渲染的页面                                                         |

打开状态每次推荐仅查询全部标签一次，再按同站点和路径生成集合并匹配候选，匹配成本为 `O(T + P)`；同路径多个标签不叠乘，也不对每个候选重复调用标签 API。

`2 MiB` 是序列化内容预算，不是 IndexedDB 物理磁盘大小，也不是浏览器总内存。`getVisits()` 仅接受 URL，不能在 API 层限制时间或返回条数；最多同时有 6 份原始响应在处理中，响应返回后立即压缩成所需的日期记录。[Chrome History API](https://developer.chrome.com/docs/extensions/reference/api/history#method-getVisits)

## 旧公式基线的测量方法

- 实际 Chromium 151.0.7922.34、真实 IndexedDB，运行接入按天对数公式之前的 TypeScript 实现；界面测试加载生产构建。
- 测试机 i5-12600K、16 个逻辑 CPU、约 32 GiB 内存，分别使用原速和 6 倍 CPU 降速。
- 覆盖 100 页／1,000 事件、1,000 页／6,000 事件、2,000 页／12,000 事件，以及单页／14,000 事件。
- 最大分散场景内容约 1.95 MiB（2,046,565 字节），生成 1,600 条可推荐页面；包含短暂停留，正常评分与诊断评分分开测量。
- 评分预热后测 20 次，快照和写入测 12 次，记录中位数、P95、最大值；冷评分另列。列表打开、搜索和过期清理是单次场景测量，不称为 P95。
- 浏览器历史使用带 2 ms 延迟的 API 替身：1,000 个 URL，每个返回 200 次访问。这个数值验证调用数量、并发和处理成本，不代表真实历史数据库的磁盘延迟。
- 页面 JS 堆使用 CDP 在强制 GC 后测量；不包括浏览器进程、DOM 原生对象、图像、GPU 等全部内存。
- CPU 降速仅作用于测试页面的 renderer。没有模拟低内存、慢磁盘或整个设备；生产扩展后台 worker 也不能据此宣称已按 6 倍降速验证。[CDP CPU throttling](https://chromedevtools.github.io/devtools-protocol/tot/Emulation/#method-setCPUThrottlingRate)

本轮将 Popup 及主题 provider 的入口改为直接引用所需模块；当前 Chrome 生产入口与其静态依赖共约 330 kB，初版实现约 1,100 kB，均为未压缩的构建文件大小，不是网络传输量或启动时间。没有新增缓存、Worker 或依赖。以 T 为标签、H 为历史、Q 为保存记录、L 为平均文本长度，站点候选整理上界为 O(T log T + H log H + (T + H)L)，额外空间 O(T + H)；搜索匹配全体候选，保存记录沿用既有搜索排序，DOM 挂载最多 20 行。API 等待与 URL 整理分别处理，不对每行重复扫描全部标签。
