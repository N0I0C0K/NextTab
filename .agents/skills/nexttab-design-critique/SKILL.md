# NextTab Design Critique

找出完成任务时真正增加理解或操作成本的地方，保留 NextTab 简洁、轻量的方向。默认只评审，不修改 UI、产品规则或文件；用户已授权修复时再按该范围实施。

## 范围与依据

- 以用户指定的界面和路径为边界，明确起点、目标、关键状态和涉及文件；没有指定时，先从「首页搜索 → 找到页面 → 打开／切换」这一条路径开始，说明范围，不扩展成全产品审计。
- 先读 [现有产品要求](../../../doc/DESIGN_REQUIREMENTS.md) 和 [NextTab UI 规范](../nexttab-ui-style/SKILL.md) 的相关部分；用户最新决定优先，其次是现有项目规范，本 skill 的通用评审建议不能覆盖它们。复用现有产品文档，不新建或臆造 PRODUCT／DESIGN 事实。
- 按路径查看必要的组件、状态和测试。关注用户能否辨认目标、理解打开与切换的区别、保留搜索／选择上下文，以及完成失败后的重试或返回；只检查与本次范围有关的项目。

## 观察与判断

- 将证据分为代码／测试依据、实际浏览器操作、已查看的截图，以及尚待验证的推断。注明文件行号或截图位置、状态及相关视口／主题；没有实际操作或查看像素，就不能写「已复现」「截图显示」或断言视觉表现。静态截图不能证明交互正常。
- 有可用且获准的本地预览时，沿限定路径观察实际渲染；根据问题选择键盘、窄屏／短窗口、长标题、空结果或失败状态，不强制遍历所有组合。无法预览时继续做有限的源码评审，明确视觉／交互证据缺口和最小补验步骤。
- 解释谁在什么情境下受影响、额外要理解什么或多做什么操作；优先降低寻找、辨认、选择、恢复的成本，不凭感觉增加装饰、说明、按钮或隐藏现有信息。没有测量时不虚构耗时或用户比例。
- 将违反已确认行为的客观缺陷、需要产品决定的 UX 取舍、个人审美偏好分开。偏好不是 bug，未知不是缺陷；缺乏证据的怀疑列为待验证，不占用已确认发现。

## 交付

先写范围、依据与验证限制，再按用户影响和发生条件排序，**最多 3 项**；可以少于 3 项或没有发现，不凑数。每项保持简短并包含：

- **优先级与类型**：P1 阻断主要任务／容易误操作，P2 明显但可绕过的阻力，P3 低影响；标明客观缺陷、UX 取舍或主观偏好。
- **受影响的人与成本**：触发情境、额外认知负担或操作步骤。
- **证据**：具体位置、实际观察或代码依据；推断和未知单独注明。
- **最小改进**：沿用既有组件、文案与交互，说明取舍，不给无关重设计方案。
- **验证**：已执行的检查、尚未确定的部分，以及如何观察改进是否有效。

结尾给出最值得先处理的一项及理由；没有高置信度问题就说明本次范围内未发现，不宣称全产品无问题。审查报告默认留在对话中；用户要求保存时遵循 AGENTS.md 的设计材料目录规则。

## 边界与配合

- 正确性或竞态问题交由 [nexttab-code-review](../nexttab-code-review/SKILL.md) 深入，真正实施 UI 改动时遵循 NextTab UI 规范及 [开发验证说明](../../../DEVELOPMENT.md)。不因本 skill 自动启动独立 agent 或全量审计。
- 本入口只包含文档规则，不安装或运行 Impeccable，不添加 hooks、检测器、二进制、联网／遥测流程、CI 或运行时依赖；无需每次评审下载外部指南。
